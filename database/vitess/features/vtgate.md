# vitess — vtgate

VTGate (`vtgate`) is the single global entry point for application queries in a Vitess deployment: a lightweight, horizontally scalable proxy that applications connect to as if it were a MySQL server. It parses SQL, builds an execution plan against the keyspace's VSchema, routes each piece of work to the correct VTTablets, and reassembles the results into one response. Applications never address shards, keyspaces, or tablets directly — they talk to VTGate, which does all the routing.

## What it is

- **Protocol bridge.** VTGate speaks both the MySQL wire protocol and Vitess's own gRPC protocol (`VTGateService`), so clients can be ordinary MySQL drivers or Vitess-aware Go clients. [VTGate](https://vitess.io/docs/24.0/concepts/vtgate/)
- **Stateless router.** VTGate holds no data; its state is cached VSchema, cached schemas, cached tablet connections, and a query plan cache. Multiple VTGate instances can front the same keyspace behind a load balancer.
- **Parser + planner.** Every statement is parsed by Vitess's SQL parser and turned into an execution plan — a tree of operators that specifies what runs where (single tablet, single shard, or all shards). [Execution plans](https://vitess.io/docs/24.0/concepts/execution-plans/)
- **Routing engine.** Using the keyspace's VSchema and vindexes, VTGate computes a keyspace ID from the sharding key and sends each query fragment to the shard(s) that own the relevant key ranges. When a query cannot be pinned to a shard it is *scattered* to all shards and merged. [Sharding](https://vitess.io/docs/24.0/concepts/sharding/)
- **Transaction coordinator.** Multi-shard writes run inside 2PC (XA-style) transactions coordinated by VTGate, so a transaction that spans shards commits or rolls back atomically.

## How it works

- **Parse.** Statements are parsed by Vitess's parser in `go/sqlparser/`, producing an AST that is independent of any specific MySQL server.
- **Plan.** The planner in [`go/vt/vtgate/planbuilder/planner.go`](https://github.com/vitessio/vitess/blob/main/go/vt/vtgate/planbuilder/planner.go) (`Planner`) walks the AST against the keyspace's VSchema and builds a plan — a tree of operators with one file per statement family: [`planbuilder/select.go`](https://github.com/vitessio/vitess/blob/main/go/vt/vtgate/planbuilder/select.go), [`insert.go`](https://github.com/vitessio/vitess/blob/main/go/vt/vtgate/planbuilder/insert.go), [`update.go`](https://github.com/vitessio/vitess/blob/main/go/vt/vtgate/planbuilder/update.go), [`delete.go`](https://github.com/vitessio/vitess/blob/main/go/vt/vtgate/planbuilder/delete.go), plus [`ddl.go`](https://github.com/vitessio/vitess/blob/main/go/vt/vtgate/planbuilder/ddl.go), [`show.go`](https://github.com/vitessio/vitess/blob/main/go/vt/vtgate/planbuilder/show.go), [`set.go`](https://github.com/vitessio/vitess/blob/main/go/vt/vtgate/planbuilder/set.go), [`window.go`](https://github.com/vitessio/vitess/blob/main/go/vt/vtgate/planbuilder/window.go), [`vexplain.go`](https://github.com/vitessio/vitess/blob/main/go/vt/vtgate/planbuilder/vexplain.go), and [`vstream.go`](https://github.com/vitessio/vitess/blob/main/go/vt/vtgate/planbuilder/vstream.go). Plans are cached per VSchema version (`PlanCache` in [`go/vt/vtgate/executor.go`](https://github.com/vitessio/vitess/blob/main/go/vt/vtgate/executor.go)), so repeated statements skip planning.
- **Execute.** The `Executor` in [`go/vt/vtgate/executor.go`](https://github.com/vitessio/vitess/blob/main/go/vt/vtgate/executor.go) runs the plan. The operator implementations live in [`go/vt/vtgate/engine/`](https://github.com/vitessio/vitess/tree/main/go/vt/vtgate/engine) (routing, joins such as [`join.go`](https://github.com/vitessio/vitess/blob/main/go/vt/vtgate/engine/join.go) and [`hash_join.go`](https://github.com/vitessio/vitess/blob/main/go/vt/vtgate/engine/hash_join.go), [`aggregations.go`](https://github.com/vitessio/vitess/blob/main/go/vt/vtgate/engine/aggregations.go), [`filter.go`](https://github.com/vitessio/vitess/blob/main/go/vt/vtgate/engine/filter.go), [`limit.go`](https://github.com/vitessio/vitess/blob/main/go/vt/vtgate/engine/limit.go), DML such as [`insert.go`](https://github.com/vitessio/vitess/blob/main/go/vt/vtgate/engine/insert.go) and [`delete.go`](https://github.com/vitessio/vitess/blob/main/go/vt/vtgate/engine/delete.go), DDL in [`ddl.go`](https://github.com/vitessio/vitess/blob/main/go/vt/vtgate/engine/ddl.go)/[`dbddl.go`](https://github.com/vitessio/vitess/blob/main/go/vt/vtgate/engine/dbddl.go), FK checks in [`fk_cascade.go`](https://github.com/vitessio/vitess/blob/main/go/vt/vtgate/engine/fk_cascade.go)/[`fk_verify.go`](https://github.com/vitessio/vitess/blob/main/go/vt/vtgate/engine/fk_verify.go)). Evaluation starts at the leaf operators, which pull from VTTablets or evaluate locally, and pipes rows up the tree to the root, which produces the final result. The plan/execution boundary and transaction handling live in [`go/vt/vtgate/plan_execute.go`](https://github.com/vitessio/vitess/blob/main/go/vt/vtgate/plan_execute.go).
- **Pick tablets.** For each routed query, the `TabletPicker` ([`go/vt/discovery/tablet_picker.go`](https://github.com/vitessio/vitess/blob/main/go/vt/discovery/tablet_picker.go)) selects a concrete tablet per shard from the health-checked topology: the `HealthCheck` in [`go/vt/discovery/healthcheck.go`](https://github.com/vitessio/vitess/blob/main/go/vt/discovery/healthcheck.go) continuously watches tablet gRPC health streams and the topology, so failovers and resharding are picked up without VTGate restarts. Connections and buffering are managed by the `TabletGateway` in [`go/vt/vtgate/tabletgateway.go`](https://github.com/vitessio/vitess/blob/main/go/vt/vtgate/tabletgateway.go), with the tablet buffer in [`go/vt/vtgate/buffer/`](https://github.com/vitessio/vitess/tree/main/go/vt/vtgate/buffer) and load balancing in [`go/vt/vtgate/balancer/`](https://github.com/vitessio/vitess/tree/main/go/vt/vtgate/balancer).
- **Track schemas and VSchema.** The per-keyspace schema tracker (`Tracker` and `UpdateController` in [`go/vt/vtgate/schema/`](https://github.com/vitessio/vitess/tree/main/go/vt/vtgate/schema)) keeps table/column metadata current, while `VSchemaManager` ([`go/vt/vtgate/vschema_manager.go`](https://github.com/vitessio/vitess/blob/main/go/vt/vtgate/vschema_manager.go)) watches the topology's `SrvVSchema` and rebuilds the in-memory VSchema — the vindexes that turn sharding keys into keyspace IDs — on every change.
- **Transactions.** `TxConn` ([`go/vt/vtgate/tx_conn.go`](https://github.com/vitessio/vitess/blob/main/go/vt/vtgate/tx_conn.go)) tracks in-flight transactions and coordinates two-phase commit across shards; per-shard 2PC state lives in the `txresolver` package ([`go/vt/vtgate/txresolver/`](https://github.com/vitessio/vitess/tree/main/go/vt/vtgate/txresolver)), with a debug helper in [`debug_2pc.go`](https://github.com/vitessio/vitess/blob/main/go/vt/vtgate/debug_2pc.go).
- **Observability.** VTGate exposes query-level stats via [`go/vt/vtgate/logstats/`](https://github.com/vitessio/vitess/tree/main/go/vt/vtgate/logstats), a `/queryz` endpoint showing cached plans ([`go/vt/vtgate/queryz.go`](https://github.com/vitessio/vitess/blob/main/go/vt/vtgate/queryz.go)), and per-shard query status aggregation ([`go/vt/vtgate/status.go`](https://github.com/vitessio/vitess/blob/main/go/vt/vtgate/status.go)). Individual statements can be inspected with `VExplain` (planned in [`planbuilder/vexplain.go`](https://github.com/vitessio/vitess/blob/main/go/vt/vtgate/planbuilder/vexplain.go)).

## Supported operations

- **DML over sharded tables.** `SELECT`, `INSERT`, `UPDATE`, `DELETE` — routed by vindex to the owning shard, scattered and merged when not routable, or rewritten for parallel execution. [Query rewriting](https://vitess.io/docs/24.0/concepts/query-rewriting/)
- **DDL.** Declarative schema changes applied across all shards of a keyspace, plus passthrough of plain DDL to tablets. [Declarative migrations](https://vitess.io/docs/24.0/user-guides/schema-changes/declarative-migrations/)
- **Transactions.** Single-shard and multi-shard transactions; multi-shard writes commit via 2PC coordinated at VTGate.
- **Prepared statements.** `Prepare`/execute flow with per-session plan caching.
- **Session and system variables.** `SET` statements and session-scoped variables maintained per connection ([`planbuilder/set.go`](https://github.com/vitessio/vitess/blob/main/go/vt/vtgate/planbuilder/set.go), [`system_variables.go`](https://github.com/vitessio/vitess/blob/main/go/vt/vtgate/planbuilder/system_variables.go)).
- **Diagnostics.** `SHOW` variants, `VExplain` for statement plans, `/queryz` for cached plans.
- **gRPC API.** `Execute`, `ExecuteBatch`, `StreamExecute`, `Prepare`, `VStream`, and `BinlogDumpGTID` (GTID-based change-data-capture streaming through VTGate). [VStream](https://vitess.io/docs/24.0/concepts/vstream/)
- **Testing.** End-to-end behavior is covered by the [`go/vt/vtgate/endtoend/`](https://github.com/vitessio/vitess/tree/main/go/vt/vtgate/endtoend) suite.
